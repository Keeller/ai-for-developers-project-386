# Браузерные сквозные тест-кейсы бронирования

Эти тест-кейсы зафиксированы до первого запуска Playwright. Они проверяют
поведение через публичный web-интерфейс и реальные HTTP-запросы к Fastify с
изолированной PostgreSQL.

## Предусловия

- Приложение и PostgreSQL запущены в изолированном тестовом окружении.
- Через интерфейс управления создан и опубликован Тип события «Знакомство»
  длительностью 30 минут.
- Создан второй опубликованный Тип события «Подробная консультация»
  длительностью 60 минут.
- В Часовом поясе календаря `Europe/Moscow` задана Доступность, содержащая как
  минимум два последовательных свободных 30-минутных Слота в пределах
  14-дневного горизонта.

## TC-E2E-01 — Гость создаёт Бронирование и видит подтверждение

1. Гость открывает публичный список Типов событий.
2. Гость выбирает опубликованный Тип события «Знакомство».
3. Гость открывает календарь и выбирает дату со свободными Слотами.
4. Гость выбирает свободный Слот.
5. Гость вводит имя `Анна` и email `anna@example.com`.
6. Гость проверяет сводку и подтверждает Бронирование.

Ожидаемый результат:

- запрос выполняется через публичный интерфейс;
- показан экран успешного Бронирования с Типом события, датой, временем,
  длительностью и выбранным Часовым поясом гостя;
- имя и email отсутствуют в URL.

## TC-E2E-02 — Занятый Слот исчезает

1. После успешного TC-E2E-01 Гость возвращается на страницу того же Типа
   события.
2. Гость открывает ту же дату.

Ожидаемый результат: ранее забронированный Слот отсутствует в списке свободных
Слотов.

## TC-E2E-03 — Пересекающееся Бронирование другого Типа события отклоняется

1. Используя второй Тип события «Подробная консультация», отправить реальный
   HTTP-запрос создания Бронирования с началом, при котором его 60-минутный
   интервал пересекает Бронирование из TC-E2E-01.
2. Использовать новый idempotency key и другие допустимые контактные данные.

Ожидаемый результат:

- сервер возвращает `409` со стабильным кодом `slot_unavailable`;
- второе Бронирование не создаётся;
- правило действует глобально для всех Типов событий, а не только внутри
  исходного Типа события.

## TC-E2E-04 — Владелец видит Бронирование в общем списке

1. Владелец календаря открывает раздел предстоящих Бронирований.

Ожидаемый результат:

- Бронирование из TC-E2E-01 видно в едином списке;
- показаны snapshot названия и длительности Типа события, начало, окончание,
  имя и email Гостя;
- Бронирования отсортированы по началу в хронологическом порядке.

## Дополнительные проверки браузерного прогона

- Полный гостевой сценарий выполняется с клавиатуры.
- На мобильном viewport форма, календарь, Слоты и подтверждение остаются
  доступными без горизонтальной прокрутки.
- Во время отправки кнопка подтверждения недоступна.
- При конфликте Слота имя и email сохраняются, Слоты обновляются, а занятый
  интервал исчезает.
